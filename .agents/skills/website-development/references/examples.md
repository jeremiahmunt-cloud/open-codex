# Example briefs and invocation prompts

These are workflow examples, not claims about real properties, customers, or business results. Use the named brand only when requested. Keep the skill equally useful outside real estate.

## Luxury property collection

> Use $website-development to build a Blessed Homes AZ property collection with a moody editorial design, strong mobile navigation, property filters, detail pages, and inquiry actions. Use fictional records until approved property data is supplied. Label proposed renderings visibly.

Build a collection, detail view, gallery, and inquiry journey. Use structured content so new properties do not require duplicate page code. Make filter state and zero-results behavior clear. Keep budgets/financing out of the public bundle. If no inquiry destination exists, make the demo behavior explicit.

Evidence: mobile/desktop screenshots, filter and navigation checks, keyboard gallery review, form behavior, and public payload inspection.

## Single-property architectural concept

> Use $website-development to create a presentation site for a fictional residence called Cypress Courtyard. Include an architectural hero, material story, gallery, and contact section. The pool and all architecture imagery are concepts. Do not invent an address, price, square footage, or completion date.

Build around materials and proposed design. Keep essential copy in HTML. Use the visual-production reference for a fictional hero. Display concept captions adjacent to generated property images. Omit unknown facts instead of filling in typical luxury specifications.

Evidence: screenshot review across crops, visible concept labels, no invented specifications, and a working contact path or explicit demo state.

## Non-property service business

> Use $website-development to build a calm, modern website for a fictional independent ceramics studio. Include workshops, a gallery, accessibility information supplied in the brief, and a waitlist form. Use warm neutrals and avoid luxury real estate language. No backend is available yet.

Build a service-site hierarchy and transparent waitlist demo without fabricated submission success. Do not add property filters, valuations, Redis, or authentication. Use supplied workshop facts; omit unsupported availability and testimonials.

Evidence: mobile navigation, keyboard form behavior, honest demo states, and appropriate audience/style.

## Internal project dashboard

> Use $website-development to extend this app with project status, owner, next action, due date, and last update. Keep the existing authentication and components. Develop against fictional records; connect SharePoint only if the approved integration is available.

Inspect the architecture first. Authorize server data routes. Avoid client-bundled private data. If credentials are unavailable, provide a typed adapter and synthetic fixtures without claiming synchronization is live. Isolate any optional cache by tenant with deliberate expiration and failure behavior.

Evidence: allowed/denied access checks, filter/empty/error states, type/build results, and explicit integration status.

## Existing-site repair

> Use $website-development to fix this site's mobile menu and hero cropping. Preserve its colors, content, and framework.

Make the narrow repair; inspect affected widths and menu keyboard behavior. Do not replace the site, create a new brand strategy, or add infrastructure.
